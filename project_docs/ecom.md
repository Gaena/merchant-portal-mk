# Модуль выписки провайдера (ecom)

> Контракты API сервиса `ecom`. Сверено с кодом 14.09.2026. Как сервис устроен внутри —
> `application_description.md` §8, правила и ограничения — корневой `AGENTS.md` §10.

## 1. Назначение и состояние

- **Стек**: Spring Boot, модуль `ecom` Gradle-монорепозитория, порт `8083`.
- **Что делает**: для мерчантов с собственным онлайн-эквайрингом, чьи платежи портал не создаёт,
  читает базу платёжного шлюза TXPG (Oracle) — **только чтение** — и отдаёт выписку и справочник
  терминалов провайдера. Своя таблица в общей PostgreSQL — `provider_terminals`.
- **Состояние на 14.09.2026**: выписка собрана по SQL провайдера и проверена на выгрузке тестового
  стенда (Р-74…Р-77): 114 заказов во всех статусах провайдера — покупки, мультиклиринг, возвраты,
  реверсалы, отказы (таблица в §2.3). Справочник терминалов — по SQL провайдера (Р-79), на данных ещё
  не проверялся. Вкладка `/transactions/ecommerce` и карточка заказа работают на этом API, форма
  заведения терминала выбирает терминал из справочника (§3). Без `ECOM_TXPG_URL`, `ECOM_TXPG_USERNAME` и `ECOM_TXPG_PASSWORD`
  сервис не стартует.

Все эндпоинты требуют JWT (`Authorization: Bearer <token>`), тот же, что выдаёт `auth`.

## 2. Выписка

### 2.1. Кто что видит

Скоуп строит `EcomScopeService`: компания пользователя → её терминалы → их `merchant_rid`
(терминал провайдера за нашим терминалом).

| Роль | Видит |
|:---|:---|
| `SYSTEM_ADMIN`, `AUDITOR` | платежи по всем терминалам, заведённым в портале; терминалы провайдера без нашего терминала — не видны |
| `COMPANY_HEAD`, `COMPANY_MANAGER`, `COMPANY_EMPLOYEE` | только по терминалам своей компании |
| роль без компании | `403`, отказ пишется в журнал аудита (`TERMINAL` / `LIST` / `DENIED`) |
| нераспознанная роль | `403` |

Если у компании нет терминалов с `merchant_rid`, выписка пустая, итоги нулевые, а карточка
любого заказа — `404`. Ветки «терминалов нет — показать всё» нет.

### 2.2. Какие заказы попадают в выписку

- **Строка — заказ со всей историей**, а не операция: у DMS-платежа операций минимум две
  (авторизация и списание), построчная выдача задвоила бы платёж и его сумму (Р-74).
- **Период — по дате создания заказа** (`order_.createtime`), полуинтервал `[dateFrom, dateTo)`. Заказ
  попадает в выписку ровно одного периода и приходит с полной историей, даже если списание прошло
  после конца периода.
- **Только завершённые заказы** (Р-71): заказы в статусах `Preparing`, `Authorized` и `Expired` не
  попадают. Исключение — `Authorized` с хотя бы одним одобренным списанием (Р-76): при мультиклиринге
  заказ остаётся `Authorized` и после списания, а деньги по нему уже взяты. Заказ с незнакомым
  статусом провайдера показывается, код — в `providerStatus`. Заказ без операций (в том числе
  пробный заказ кнопки «Тест») не попадает никогда.
- **Время.** Даты в базе шлюза — местное время Asia/Baku без пояса (подтверждено провайдером); сервис
  читает их в поясе `ecom.txpg.zone` (по умолчанию `Asia/Baku`), в ответе они в UTC.

### 2.3. Деньги и статус заказа

Вид операции — поле `kind` в истории (Р-75). `trantype` у покупок всегда `Purchase`, поэтому вид
определяется по фазе, `voidkind` и возврату:

| `kind` | Признак в базе шлюза |
|:---|:---|
| `AUTHORIZATION` | `phase = Auth` — холд, денег не списывает |
| `CAPTURE` | `phase = Clearing` — списание холда; их может быть несколько (мультиклиринг) |
| `PURCHASE` | `phase = Single` — оплата одним сообщением |
| `REVERSAL` | заполнен `voidkind` (`Full`, `Partial`) |
| `REFUND` | `trantype = Refund` |
| `UNKNOWN` | всё остальное: видно в истории, в деньги не входит |

В деньги входят только операции с `resultCode = Approved`:

- `capturedAmount` — сумма `clearAmount` у `CAPTURE` и `PURCHASE` за вычетом реверсалов покупок и
  списаний (Р-77). Списания мультиклиринга складываются и до суммы заказа не обрезаются. Реверсал
  холда (`phase = Auth`, `clearAmount` 0) денег не двигает — снимает холд или его часть;
- `refundedAmount` — возвраты: сумма `clearAmount` у `REFUND` по модулю (в базе она с минусом), плюс
  отрицательный `clearAmount` у списания без `voidkind`. Реверсал возвратом не считается: он отменяет
  покупку до расчётов, и денег мерчант не получает.

`status` — первое подходящее правило сверху вниз:

| Условие | `status` |
|:---|:---|
| что-то списано, возвращено столько же или больше | `REFUNDED` |
| что-то списано, возвращена часть | `PARTIALLY_REFUNDED` |
| что-то списано, возвратов нет, списано меньше суммы заказа | `PARTIALLY_PAID` (Р-78) |
| что-то списано, возвратов нет, не меньше суммы заказа — мультиклиринг бывает и сверх неё | `SUCCESS` |
| одобрена авторизация, ничего не списано, заказ `Authorized` | `AUTHORIZED` |
| одобрена авторизация или покупка, но в итоге ничего не списано — холд снят или покупка отменена реверсалом; заказ не `Authorized` | `CANCELED` |
| возврат без списания и без одобренной авторизации или покупки | `REFUNDED`, в лог — предупреждение |
| операции были, ни одна не одобрена | `FAILED` |
| остальное: одобренные операции не разобраны | `PENDING` |

`Closed` провайдер ставит сам: заказ пробыл в `Preparing` дольше 10 минут, либо DMS-авторизацию без
списания отменили автоматически через N дней (N — на стороне провайдера).

Как это выглядит на выгрузке тестового стенда от 14.09.2026 (114 заказов, 188 операций):

| Статус провайдера ← предыдущий | Заказов | `status` |
|:---|---:|:---|
| `FullyPaid` ← `Preparing`; `Closed` ← `FullyPaid` | 8; 39 | `SUCCESS` |
| `PartPaid` ← `Preparing` — оплачено меньше суммы заказа | 5 | `PARTIALLY_PAID` |
| `Closed` ← `PartPaid` — снята часть холда, остаток списан | 7 | `PARTIALLY_PAID` |
| `Closed` ← `PartPaid` — возвращена часть списанного | 7 | `PARTIALLY_REFUNDED` |
| `Refused` ← `Authorized` | 6 | `REFUNDED` |
| `Closed` ← `Authorized`; `Cancelled` ← `Preparing` | 11; 4 | `CANCELED` |
| `Rejected` ← `Preparing` | 23 | `FAILED` |
| `Expired` ← `Preparing` | 2 | в выписку не попадают (Р-71) |
| `Rejected` ← `Authorized` — холд одобрен, не списан | 1 | `CANCELED` — по деньгам, не по коду |
| `Rejected` ← `Refused` — списано и возвращено полностью | 1 | `REFUNDED` — по деньгам, не по коду |

### 2.4. `GET /api/v1/ecom/transactions`

*Параметры*:

| Параметр | Обязателен | Что значит |
|:---|:---|:---|
| `dateFrom`, `dateTo` | да | ISO-8601 instant; `dateTo` позже `dateFrom`; период не длиннее `ecom.txpg.max-window` (по умолчанию 92 дня) |
| `merchantRids` | нет | терминалы провайдера (`merchantRid` из §2.6), можно несколько; только сужают скоуп — терминал вне скоупа отбрасывается |
| `minAmount`, `maxAmount` | нет | границы суммы заказа |
| `query` | нет | точное совпадение: номер заказа, `ridByMerchant` или RRN |
| `cursor` | нет | значение `nextCursor` предыдущей страницы |
| `size` | нет | по умолчанию 25, приводится к `1…ecom.txpg.max-page-size` (по умолчанию 200) |

*Порядок*: по номеру заказа, от новых к старым. Страница курсорная: `nextCursor` — закодированный
номер последнего заказа страницы, `null` на последней странице. Общего числа строк в ответе нет
намеренно — это второй тяжёлый запрос к базе шлюза; итоги дают `/stats`.

*Ответ* `200`:

```json
{
  "content": [
    {
      "orderId": "1234567",
      "merchantRid": "M-000123",
      "merchantTitle": "Shop LLC",
      "ridByMerchant": "ORDER-42",
      "status": "SUCCESS",
      "providerStatus": "FullyPaid",
      "providerPrevStatus": "Authorized",
      "amount": 150.00,
      "capturedAmount": 150.00,
      "refundedAmount": 0,
      "currency": "AZN",
      "description": "Order 42",
      "createdAt": "2026-09-01T10:15:00Z",
      "lastOperationAt": "2026-09-01T10:17:30Z",
      "cardMask": "426863******3689",
      "rrn": "629677123123",
      "declineCode": null,
      "operations": [
        { "tranId": "260901101600000010", "at": "2026-09-01T10:16:02Z", "kind": "AUTHORIZATION",
          "type": "Purchase", "phase": "Auth", "voidKind": null, "authKind": "Preliminary",
          "resultCode": "Approved", "amount": 150.00, "clearAmount": 0, "currency": "AZN",
          "rrn": "629677123123" },
        { "tranId": "260901101700000010", "at": "2026-09-01T10:17:30Z", "kind": "CAPTURE",
          "type": "Purchase", "phase": "Clearing", "voidKind": null, "authKind": null,
          "resultCode": "Approved", "amount": 150.00, "clearAmount": 150.00, "currency": "AZN",
          "rrn": "629677123123" }
      ]
    }
  ],
  "nextCursor": "MTIzNDU2Nw"
}
```

- `merchantRid` — reference id **мерчанта**, задаёт провайдер; `ridByMerchant` — reference id
  **платежа**, задаёт мерчант (Р-69). `ridByMerchant` **бывает `null`**: заказ, заведённый мерчантом у
  провайдера напрямую, может его не нести. Ничем не подменяется.
- `amount` — сумма заказа, `capturedAmount` — списанное; при частичном списании они различаются.
- `declineCode` — код ответа последней операции; заполнен, только когда одобренных операций не было.
- `tranId` — `tran.ridbyacq`, 18 цифр, всегда строкой: в числовой колонке (например, в Excel) последние
  знаки теряются.
- Пароля заказа из базы шлюза в ответе нет и не будет. Номера терминала, почты и телефона плательщика
  тоже нет: этих колонок нет в SQL провайдера, а отсутствующая колонка уронила бы всю выписку.

*Отказы*: `400` — нет `dateFrom` или `dateTo`, `dateTo` не позже `dateFrom`, период длиннее
предела (`The requested period exceeds the maximum of N days`), нечитаемый `cursor`
(`Invalid page cursor`); `403` — см. §2.1.

### 2.5. `GET /api/v1/ecom/transactions/stats`

Итоги по всем заказам периода по правилам §2.2 и §2.3, а не по загруженной странице.

*Параметры*: `dateFrom`, `dateTo`, `merchantRids` — те же правила, что в §2.4.

*Ответ* `200`:

```json
{
  "orderCount": 14,
  "statusCounts": { "PENDING": 0, "AUTHORIZED": 0, "SUCCESS": 10, "PARTIALLY_PAID": 0, "FAILED": 0,
                    "PARTIALLY_REFUNDED": 0, "REFUNDED": 0, "CANCELED": 4 },
  "totals": [ { "currency": "AZN", "capturedAmount": 357.00, "refundedAmount": 0 } ]
}
```

- `statusCounts` перечисляет все статусы, нулевые тоже.
- Суммы — по валютам: заказы в разных валютах не складываются.

*Отказы*: те же, что в §2.4, кроме курсора.

### 2.6. `GET /api/v1/ecom/transactions/terminals`

Источник фильтра `merchantRids`: терминалы портала в скоупе пользователя и терминал провайдера за
каждым. Читается из базы портала, к шлюзу запроса нет; параметров нет.

*Ответ* `200`: `[ { "merchantRid": "M-000123", "title": "Shop LLC", "login": "shop_login" } ]`, по
названию. `title` и `login` — из справочника терминалов провайдера (§3); пусты, если терминала в
справочнике нет.

### 2.7. `GET /api/v1/ecom/transactions/{orderId}`

Карточка заказа — тот же объект, что строка выписки (§2.4), с полной историей операций. Период не
нужен.

*Отказы*: `404` `Transaction not found` — заказа нет, он чужой, не завершён (§2.2) или номер не
число. Все четыре случая неотличимы: подобранный номер не должен подтверждать, что такой заказ у
провайдера есть.

## 3. Справочник терминалов провайдера

Слепок терминалов провайдера в таблице `provider_terminals`. По нему `directory` сверяет статусы
наших терминалов (`directory.md` §3.2), а форма заведения терминала подставляет название и логин
по `merchantRid`.

Что попадает в слепок (Р-79, SQL провайдера от 14.09.2026):

- e-commerce терминалы процессинга `70` с TID на `PBY`, у которых **и логин, и терминал** в статусе
  `Active`. Выключенный у провайдера пропадает из выгрузки и через три обновления подряд становится
  неактивным, а за ним и наш терминал (Р-66);
- `rid` — reference id мерчанта (`merchant.rid`), тот же, по которому идёт выписка; `title` — название
  мерчанта; `login` — логин терминала;
- у мерчанта одна строка. Одинаковые строки считаются одной. Если у мерчанта пришло несколько
  разных логинов, какой из них наш — неизвестно: такой мерчант в обновлении не меняется и не гаснет,
  новый не заводится, в лог — предупреждение.

### 3.1. `GET /api/v1/ecom/provider-terminals`

*Доступ*: только `SYSTEM_ADMIN` — это карта всех мерчантов провайдера; остальным `403`.
*Параметры*: `includeInactive` (`false` по умолчанию) — показать и выключенные у провайдера.
*Порядок*: по названию (для активных).

*Ответ* `200`:

```json
[ { "rid": "M-000123", "title": "Shop LLC", "login": "shop_login", "active": true,
    "lastSeenAt": "2026-09-13T08:15:00Z" } ]
```

Пароля в ответе нет: у провайдера его не спрашивают, его вводит администратор при заведении.
`lastSeenAt` пуст, если терминал не приходил ни разу.

### 3.2. `POST /api/v1/ecom/provider-terminals/sync`

Обновить слепок сейчас, не дожидаясь расписания (каждые 15 минут, `ecom.terminal-sync.cron`).

*Доступ*: только `SYSTEM_ADMIN`; остальным `403`.

*Ответ* `200`:

```json
{ "applied": true, "seen": 240, "ambiguous": 0, "disabled": 1, "skippedBecause": null }
```

- `applied: false` с причиной в `skippedBecause` — выборка не удалась или пришла пустой; слепок не
  тронут. У работающего эквайринга не бывает нуля терминалов, и такой ответ не может выключить всех.
- `ambiguous` — сколько мерчантов пришло несколькими разными строками и потому не обновлено.
- `disabled` — сколько терминалов в этом обновлении стали неактивными: терминал помечается
  неактивным после `ecom.txpg.missing-runs-before-disable` (по умолчанию 3) обновлений подряд без него.
