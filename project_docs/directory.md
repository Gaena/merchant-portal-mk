# Модуль Управления Справочниками (Directory Service)

## 1. Архитектура и Структура
-   **Стек**: Spring Boot, модуль `directory` Gradle-монорепозитория, порт `8082`.
-   **База данных**: общая PostgreSQL. Свои таблицы — `companies`, `terminals`, журнал `audit_logs`;
    нативными запросами сервис меняет статусы в `payment_links` (модуль `pbl`) и читает
    `provider_terminals` (модуль `ecom`).
-   **Связь с другими модулями**: 
    -   `directory` предоставляет эндпоинты для управления компаниями и терминалами.
    -   При создании компании или терминала данные записываются в общие таблицы `companies` и `terminals`.
    -   Модуль `auth` использует таблицу `companies` для валидации связи пользователей с компаниями.
    -   Модуль `pbl` считывает данные терминалов из таблицы `terminals` для проведения оплат через MilliKart.
    -   Модуль `ecom` обновляет справочник терминалов провайдера (`provider_terminals`), по которому
        `directory` сверяет статусы терминалов (§3.2, «Синхронизация статусов с провайдером»).

## 2. База данных (Таблицы `companies` и `terminals` в общей БД)

### 2.1. Таблица `companies`
-   `id` (VARCHAR) — Primary Key (например, буквенно-цифровой код или UUID).
-   `name` (VARCHAR) — Название юридического лица / компании.
-   `status` (VARCHAR) — Статус (`ACTIVE`, `INACTIVE`, `DELETED` — мягкое удаление).
-   `provider_login` (VARCHAR(255), уникальный, может быть `NULL`) — логин компании к провайдеру,
    целиком, с префиксом владельца (с 24.09.2026, Р-93): с ним идут все запросы `pbl` к шлюзу.
-   `provider_password` (VARCHAR(512), может быть `NULL`) — пароль к провайдеру, **только шифротекст**
    AES-256-GCM (`CredentialCipher`, ключ `CREDENTIALS_ENCRYPTION_KEY`). `NULL` у компаний, заведённых
    до Р-93: `pbl` отказывает им до обращения к провайдеру.
-   `created_at` (TIMESTAMP).

### 2.2. Таблица `terminals`
-   `id` (INTEGER) — Primary Key (идентификатор терминала в MilliKart).
-   `name` (VARCHAR) — Пользовательское имя (например, "Касса 1").
-   `login` (VARCHAR) — логин терминала у провайдера, из справочника. К шлюзу с ним больше не ходят
    (Р-93), выписка его тоже не читает (Р-97); на нём держится сверка, а подписью он служит терминалам без номера.
-   `terminal_rid` (VARCHAR(64), может быть `NULL`) — номер терминала у провайдера (`txpg.terminal.rid`,
    с 24.09.2026, Р-96): с ним `pbl` создаёт заказ (`POST /order?terminalRid=…`), им терминал подписан на
    экранах. Берётся из справочника при заведении и обновляется сверкой. Пусто у терминалов, заведённых
    до Р-96 без справочника: платежи по ним — `400`.
-   `company_id` (VARCHAR) — Foreign Key на `companies.id`.
-   `status` (VARCHAR(16), `NOT NULL DEFAULT 'ACTIVE'`) — `ACTIVE` или `BLOCKED` (P2-8).
    Колонку добавляют **оба** сервиса (`directory/005-terminal-status.xml` и
    `pbl/005-terminal-status.xml`), каждый под своим преконтролем: таблицу создаёт тот, кто
    стартовал первым, и колонка нужна обоим (P1-2).
-   `status_source` (VARCHAR(16), `NOT NULL DEFAULT 'MANUAL'`) — кто выключил терминал: `MANUAL`
    (человек) или `PROVIDER` (синхронизация). С 12.09.2026, `directory/006` и `ecom/002`.
-   `merchant_rid` (VARCHAR(64), уникальный, может быть `NULL`) — терминал провайдера, за которым
    стоит наш (`merchantRid` у провайдера, Р-69). Один терминал провайдера — одна наша компания.

## 3. API Контракты (Эндпоинты `directory`)

Все эндпоинты защищены проверкой JWT токена (сигнатура валидируется ключом `HS256`).

### 3.1. Управление Компаниями (Companies CRUD)
-   `POST /api/v1/companies` — Создать компанию.  
    *Доступ*: Только `SYSTEM_ADMIN`.  
    *Запрос*: `{"id": "comp-01", "name": "MilliKart LLC", "providerLogin": "TerminalSys/merchant", "providerPassword": "…"}`  
    Логин и пароль к провайдеру **обязательны** (с 24.09.2026, Р-93). Логин — целиком, с префиксом
    владельца, сохраняется как пришёл; пароль ложится шифротекстом.  
    **Логин — только активный мультимерчант** (Р-94): `MultiMerchantSys/<login>`, и в слепке логинов
    `provider_logins` (`ecom.md` §3.3) он `Active` и связан хотя бы с одним мерчантом со связью `Active`.
    Проверяется только при сохранении — заведении или смене логина; уже сохранённые логины слепок не
    трогает.  
    *Отказы*: `400` — нет поля; компания с таким `id` уже есть; `Provider login must be a multimerchant
    login: MultiMerchantSys/<login>`; `The provider login list has not been synchronised yet; refresh the
    provider directory and try again` (слепка нет — `ecom` не развёрнут — или он пуст); `Provider login …
    is not in the synchronised list of multimerchant logins`; `… is not active at the provider`; `… has no
    active merchants at the provider`. `409` — `Provider login is already used by another company`
    (логин уникален, удалённые компании его не освобождают).  
    *Ответ*: `CompanyResponse` — `id`, `name`, `status`, `providerLogin`, аудит-поля. **Пароля в
    ответах нет никогда**; `providerLogin` заполнен только для `SYSTEM_ADMIN`, остальным — `null`
    (так во всех ответах о компании).
-   `GET /api/v1/companies` — Получить список компаний. **Постранично с 22.08.2026 (P2-1)**.  
    *Доступ*: `SYSTEM_ADMIN` и `AUDITOR`.  
    *Параметры*: `page` (по умолчанию `0`), `size` (по умолчанию `20`) — те же умолчания и тот же
    потолок `200`, что у `GET /api/v1/audit-logs`. Значения срезаются, а не отклоняются:
    `?page=-1&size=0` отвечает `200`, а не `500`. С 24.08.2026 (P3-1) — `search`: подстрока без
    учёта регистра по `name` и `id`; `%` и `_` ищутся буквально; пустая строка — то же, что
    отсутствие параметра, длиннее 100 символов — обрезается. `totalElements` считает
    отфильтрованное.  
    *Порядок*: по `name`, при совпадении — по `id`. Довесок обязателен: без него две компании
    с одинаковым названием могут попасть на обе соседние страницы или ни на одну.  
    *Ответ*: `PagedResponse` — `{"content": [...], "totalElements", "totalPages", "size", "number"}`
    (раньше был голый массив). Компании со статусом `DELETED` не входят ни в `content`, ни
    в `totalElements` — фильтр выполняется в запросе.
-   `GET /api/v1/companies/provider-logins` — свободные логины мультимерчантов для формы компании
    (с 24.09.2026, Р-95).  
    *Доступ*: только `SYSTEM_ADMIN`; остальным — `403` с записью `COMPANY` / `LIST` в журнал.  
    *Ответ*: `[{"login": "MultiMerchantSys/bazarstore@company.com", "merchants": ["BazarStore Genclik",
    "BazarStore PortBaku"]}]`, по логину. В списке — логины из слепка `provider_logins`, которые пройдут
    проверку при сохранении (`Active` и хотя бы одна связь `Active` с мерчантом), и которых нет ни у одной
    компании, включая удалённые. `merchants` — названия мерчантов активных связей. Слепка нет или пуст —
    пустой список. Список — подсказка форме: `POST` и `PATCH` проверяют логин сами.
-   `GET /api/v1/companies/{id}` — Детали компании.  
    *Доступ*: `SYSTEM_ADMIN` и `AUDITOR` — любой; остальные роли — только своей компании.
-   `PATCH /api/v1/companies/{id}` — Редактировать компанию.  
    *Доступ*: Только `SYSTEM_ADMIN`.  
    *Запрос* (все поля необязательны, пустое — «не менять»): `{"name", "status", "providerLogin",
    "providerPassword"}`. Новый пароль ложится шифротекстом; прочитать прежний нельзя. Новый логин
    проверяется по слепку так же, как при создании; тот же логин проверку не запускает. Журнал —
    `COMPANY` / `UPDATE` с `Provider login changed from 'X' to 'Y'` и `Provider password changed`, без
    значения пароля. Занятый логин — `409`.  
    *Статус*: только `ACTIVE` или `INACTIVE`, сравнение точное; иное — `400` `Company status must be ACTIVE
    or INACTIVE` (с 25.09.2026). `DELETED` ставит только `DELETE`, со своей записью в журнале. Смена
    статуса пишет ещё `BLOCK`/`UNBLOCK`.
-   `DELETE /api/v1/companies/{id}` — Удалить/деактивировать компанию.  
    *Доступ*: Только `SYSTEM_ADMIN`.

### 3.2. Управление Терминалами (Terminals CRUD)

Заводит терминал только `SYSTEM_ADMIN` (с 24.09.2026, Р-93). Правка разрешена ролям из
`TerminalService.TERMINAL_WRITE_ROLES` = `SYSTEM_ADMIN`, `COMPANY_HEAD`, `COMPANY_MANAGER`. Роль проверяется **до** `companyId`, поэтому
`COMPANY_EMPLOYEE`, `AUDITOR` и любая нераспознанная роль получают `403` даже на терминалы своей
компании (P1-15, 17.08.2026). Чтение шире: свои терминалы видят все компанейские роли, включая
`COMPANY_EMPLOYEE`, а `SYSTEM_ADMIN` и `AUDITOR` — все.

-   `POST /api/v1/terminals` — Создать терминал.  
    *Доступ*: только `SYSTEM_ADMIN` (с 24.09.2026, Р-93); остальным — `403` с записью в журнал.  
    *Запрос*: `{"companyId": "comp-01", "merchantRid": "E1120020"}` — оба поля обязательны. Терминал
    выбирается из справочника провайдера: `name`, `login` и `terminalRid` берутся оттуда, пароля у
    терминала нет — к провайдеру ходят с кредами компании. Ручное заведение с названием и логином снято.
    **Мерчант должен быть связан с логином компании** (Р-96): активная связь в слепке `provider_logins`
    (`ecom.md` §3.3); форме список таких терминалов отдаёт `GET /api/v1/terminals/provider-terminals`.  
    **Номер терминала выдаёт база** (с 14.09.2026, Р-81): `id` в запросе не нужен, а присланный
    игнорируется; номер приходит в ответе. На живой базе нумерация продолжается после наибольшего
    существующего номера.  
    *Отказы (`400`)*: нет поля; компании нет; `merchantRid` уже привязан к другому терминалу
    (`Provider terminal … is already linked to terminal …`); `merchantRid` нет в справочнике
    (`… is not in the synchronised list`); у строки справочника нет названия, логина или номера
    терминала; мерчант не связан с логином компании (`Provider terminal … does not belong to the
    multimerchant login of company …`).
-   `GET /api/v1/terminals/provider-terminals?companyId=…` — терминалы провайдера для формы заведения
    (с 24.09.2026, Р-96).  
    *Доступ*: только `SYSTEM_ADMIN`; остальным — `403` с записью `TERMINAL` / `LIST`.  
    *Ответ*: `[{"rid": "223456789054323", "title": "BazarStore PortBaku", "login": "BS00003",
    "terminalRid": "BS00003"}]`, по названию. Только активные строки справочника с номером терминала,
    чей мерчант связан активной связью с логином компании, и которые ещё не заведены ни в одной компании
    (один терминал провайдера — одна компания). Нет `companyId` или компании — `400`.
-   `GET /api/v1/terminals` — Список терминалов. **Постранично с 22.08.2026 (P2-1)**.  
    *Доступ*: `SYSTEM_ADMIN` и `AUDITOR` (все), `COMPANY_HEAD`/`COMPANY_MANAGER`/`COMPANY_EMPLOYEE`
    (только терминалы своей компании; без `companyId` — `403`).  
    *Параметры*: `page` (`0`), `size` (`20`, потолок `200`) — значения срезаются, а не отклоняются.
    С 24.08.2026 (P3-1) — `search`: подстрока без учёта регистра по `name`, `login`, `id` (как
    тексту), `companyId` и **названию компании**; `%` и `_` ищутся буквально; пустая строка — то
    же, что отсутствие параметра. Поиск работает **внутри** ролевого скоупа: компания видит только
    свои терминалы, что бы ни искала.  
    *Порядок*: по `name`, при совпадении — по `id`.  
    *Ответ*: `PagedResponse` (раньше — голый массив).
-   `GET /api/v1/terminals/options` — **лёгкий список терминалов** для выпадающих списков и
    подстановки имён (решение Р-45, 22.08.2026).  
    *Доступ*: тот же, что у `GET /api/v1/terminals`.  
    *Ответ*: голый массив из пяти полей, без пагинации (`terminalRid` — с 24.09.2026, Р-96):
    ```json
    [ {"id": 998877, "name": "Main Terminal", "login": "term_login", "terminalRid": "BS00003", "status": "ACTIVE"} ]
    ```
    **`login` здесь есть с 11.09.2026** (Р-59): мерчант узнаёт терминал по логину, и экраны
    подписывают им терминал. Новой видимости это не даёт — постраничный список отдаёт логин тем же
    ролям. Пароля у терминала нет вовсе (Р-93).

    **Заблокированные терминалы в ответе есть, и убирать их нельзя.** У эндпоинта два
    потребителя с разными нуждами: форме создания ссылки нужны только `ACTIVE` (на
    заблокированном терминале бэкенд откажет — P2-8), а экрану транзакций и карточке транзакции
    нужны **все**, потому что они подставляют имя терминала в старые платежи, и по снятому
    с обслуживания терминалу имя должно остаться. Поэтому фильтрует потребитель, а не сервер.
-   `GET /api/v1/terminals/{id}` — Детали терминала.  
    *Доступ*: `SYSTEM_ADMIN`, `AUDITOR`, любая роль с `companyId` терминала (в т.ч. `COMPANY_EMPLOYEE`).  
    *Ответ*: `TerminalResponse` — `id`, `name`, `login`, `terminalRid`, `companyId`, `status`, аудит-поля.
-   **`GET /api/v1/terminals/{id}/password` больше нет** (с 24.09.2026, Р-93) — `404`: пароля у
    терминала нет.
-   `PATCH /api/v1/terminals/{id}` — Редактировать терминал **и его статус**.  
    *Доступ*: `SYSTEM_ADMIN`, `COMPANY_HEAD`/`COMPANY_MANAGER` (своей компании).  
    *Запрос* (все поля необязательны): `{"name": "...", "companyId": "...", "status": "ACTIVE" | "BLOCKED"}`.
    Логин не правится — его меняет только сверка со справочником; `login` и `password` в теле
    игнорируются.  
    *Компания*: терминал переходит только в компанию, с логином мультимерчанта которой его мерчант
    (`merchant_rid`) активно связан в `provider_logins`, — то же правило, что при заведении (Р-96, Р-97).
    Иначе `400` `Terminal … cannot be moved to company …: its provider merchant is not linked to the
    multimerchant login of that company`; терминал без `merchant_rid` не переносится вовсе. Та же
    компания в запросе — не перенос, проверки нет.  
    *Статус*: ручная смена ставит `status_source = MANUAL`. Терминал, выключенный синхронизацией
    (`status_source = PROVIDER`), вручную не включается — `403` `Terminal … is out of service at the
    provider and will be unblocked automatically once the provider brings it back`.
-   **`DELETE /api/v1/terminals/{id}` больше нет** — метод отвечает `405` (путь существует, глагол не поддерживается).

> **Терминалы не удаляются, а блокируются** (P2-8, 21.08.2026, решение Р-37). Терминал, через
> который прошёл хоть один платёж, удалить нельзя в принципе: на него ссылаются платёжные ссылки
> (`fk_payment_links_terminal`), и попытка удаления возвращала `500` вместо внятного отказа.
> Вместо удаления — `status`:
>
> - `ACTIVE` — терминал в работе (значение по умолчанию для всех существующих терминалов);
> - `BLOCKED` — терминал выведен из работы.
>
> **Блокировка запрещает только новые платежи** (Р-38): создание ссылки на таком терминале — `400`,
> открытие ссылки плательщиком — отказ. Возвраты, списание холдов DMS и проверка статуса по уже
> прошедшим платежам продолжают работать; убирать эти исключения нельзя — иначе холд зависнет на
> карте клиента, а возврат не дойдёт до плательщика.
>
> **Блокировка приостанавливает ссылки терминала** (Р-39): `ACTIVE` → `SUSPENDED` одним `UPDATE`
> в той же транзакции, что и смена статуса терминала. `EXPIRED`, `COMPLETED` и `CANCELED` не
> трогаются. Разблокировка (Р-40) возвращает `SUSPENDED` → `ACTIVE`, а тем, у кого срок истёк за
> время блокировки, ставит `EXPIRED`. Обе операции пишутся в журнал аудита отдельными действиями
> `BLOCK` / `UNBLOCK` с числом затронутых ссылок в `details`.
>
> Ручная блокировка **локальна для портала**: в MilliKart терминал продолжает работать, и платёж,
> начатый в обход портала, пройдёт. Обратное направление есть — синхронизация ниже.

#### Синхронизация статусов с провайдером (с 12.09.2026, Р-66)

Сервис `ecom` каждые 15 минут обновляет справочник терминалов провайдера (`provider_terminals`),
а `directory` по расписанию `directory.terminal-reconciliation.cron` (по умолчанию тоже каждые
15 минут) сверяет с ним `terminals`:

| Наш терминал | У провайдера | Что происходит |
|:---|:---|:---|
| `ACTIVE` | неактивен | `BLOCKED`, `status_source = PROVIDER`, активные ссылки → `SUSPENDED` |
| `BLOCKED`, `status_source = PROVIDER` | снова активен | `ACTIVE`, ссылки возвращаются, просроченные → `EXPIRED` |
| `BLOCKED`, `status_source = MANUAL` | любое | не трогается — это решение клиента |
| без `merchant_rid` или не найден в справочнике | — | не трогается: отсутствие строки — «не знаем» |

Пустой справочник (синхронизация ещё не проходила или `ecom` не установлен) не применяется вовсе.
Провайдер считается выключившим терминал только после трёх обновлений подряд без него. Смену
названия, логина и номера терминала (`terminal_rid`, Р-96) у провайдера сверка переносит к нам и пишет
в журнал `TERMINAL` / `UPDATE` от `system`. Смены
статуса пишутся в журнал как `TERMINAL` / `BLOCK` или `UNBLOCK` с исполнителем `system`.

### 3.3. Журнал аудита (Audit Logs)

-   `GET /api/v1/audit-logs` — Журнал действий над компаниями и терминалами.
    *Доступ*: `SYSTEM_ADMIN` и `AUDITOR` — записи всех компаний; `COMPANY_HEAD`/`COMPANY_MANAGER` —
    только своей компании; остальные роли — `403` (и сам отказ записывается в журнал).
    *Параметры* (все необязательные и **независимые** — с 24.08.2026, P3-1; до этого
    `entityType` без `entityId` молча игнорировался): `entityType` (сравнение без учёта
    регистра), `entityId` (без учёта регистра), `search` — подстрока без учёта регистра по
    `performedBy`, `action`, `entityId` и `details`, `%` и `_` ищутся буквально; `outcome`
    (`SUCCESS` / `DENIED` / `UNRESOLVED`, неизвестное значение — как отсутствие фильтра);
    `from` и `to` — граница по `createdAt`, ISO-instant (`2026-08-24T10:15:30Z`) или просто дата
    (`2026-08-24` — весь день по UTC), неразбираемое значение — как отсутствие фильтра;
    `page` (по умолчанию `0`), `size` (по умолчанию `20`) — те же умолчания, что у
    `GET /api/v1/transactions` в `pbl`. Значения срезаются, а не отклоняются: `size` приводится
    к диапазону `1…200`, `page` — не меньше нуля, поэтому `?size=0` отвечает 200, а не 500.
    *Ответ* (с 21.08.2026 пагинированный — `PagedResponse`, раньше был голый массив):
    ```json
    {
      "content": [
        {
          "id": "…", "entityType": "COMPANY", "entityId": "comp-01", "action": "CREATE",
          "performedBy": "admin@millikart.az", "companyId": "comp-01",
          "details": "Created company: MilliKart LLC",
          "clientIp": "203.0.113.9", "outcome": "SUCCESS", "createdAt": "…"
        }
      ],
      "totalElements": 1, "totalPages": 1, "size": 20, "number": 0
    }
    ```
    Порядок — всегда от новых к старым (`createdAt DESC`, при равенстве — `id DESC`: одна
    операция пишет несколько событий в одну миллисекунду, и без уникального довеска записи с
    равным временем прыгали бы между страницами — P3-1). `outcome` — `SUCCESS`, `DENIED` или
    `UNRESOLVED` (с 24.08.2026, P3-2): успешное действие записывается **после коммита** его
    транзакции (откатившееся действие в журнал не попадает), отказ в доступе — сразу, в своей
    транзакции (Р-35); `UNRESOLVED` — денежная операция, исход которой эквайер не подтвердил:
    локальная транзакция откатилась, и эта запись — единственный след, по которому сверяются
    с эквайером. `clientIp` — адрес клиента по правилам `ClientIp` (заголовкам верим только от
    доверенного прокси); `null`, если действие выполнено вне HTTP-запроса. У записи об отказе
    `companyId` — компания **того, кто пытался**, а не та, что названа в запросе (иначе через
    отказ можно было бы писать текст в обзор аудита чужой компании); что именно пытались
    сделать, видно в `entityId` и `details`. Журнал только пополняется — записи не правятся и не
    удаляются (приложение физически не умеет: у репозитория записи один метод `save`, у сущности
    нет сеттеров). С 22.08.2026 (P2-14) сюда попадают записи **всех трёх сервисов**: `directory`
    — компании и терминалы, `auth` — учётные записи и аутентификация (`entityType` `USER` и
    `AUTH`), `pbl` — ссылки и деньги (`PAYMENT_LINK`, `TRANSACTION`), а также проверки терминала у
    провайдера; с 12.09.2026 — и `ecom` (отказ в выписке пользователю без компании). С 24.08.2026 (P3-2)
    значения `entityType` и `action` заданы общим словарём (`AuditEntity` / `AuditAction` в
    `common`); полная таблица событий — что лежит в `entityId`, кто пишет, что в `details` — в
    `technical_handover.md` §4.4. Машинерия записи общая, в `az.millikart.common.audit`; читает
    журнал только этот эндпоинт.
