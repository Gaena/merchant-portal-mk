# Модуль Управления Справочниками (Directory Service)

## 1. Архитектура и Структура
-   **Стек**: Java Spring Boot (независимый подпроект в папке `directory`, порт `8082`).
-   **База данных**: Общая PostgreSQL база данных `postgres` (общие таблицы `companies`, `terminals`, `users`).
-   **Связь с другими модулями**: 
    -   `directory` предоставляет эндпоинты для управления компаниями и терминалами.
    -   При создании компании или терминала данные записываются в общие таблицы `companies` и `terminals`.
    -   Модуль `auth` использует таблицу `companies` для валидации связи пользователей с компаниями.
    -   Модуль `pbl` считывает данные терминалов из таблицы `terminals` для проведения оплат через MilliKart.

---

## 2. База данных (Таблицы `companies` и `terminals` в общей БД)

### 2.1. Таблица `companies`
-   `id` (VARCHAR) — Primary Key (например, буквенно-цифровой код или UUID).
-   `name` (VARCHAR) — Название юридического лица / компании.
-   `status` (VARCHAR) — Статус (`ACTIVE`, `SUSPENDED`, `DELETED`).
-   `created_at` (TIMESTAMP).

### 2.2. Таблица `terminals`
-   `id` (INTEGER) — Primary Key (идентификатор терминала в MilliKart).
-   `name` (VARCHAR) — Пользовательское имя (например, "Касса 1").
-   `login` (VARCHAR) — Логин для API MilliKart.
-   `password` (VARCHAR) — Пароль для API MilliKart.
-   `company_id` (VARCHAR) — Foreign Key на `companies.id`.
-   `status` (VARCHAR(16), `NOT NULL DEFAULT 'ACTIVE'`) — `ACTIVE` или `BLOCKED` (P2-8).
    Колонку добавляют **оба** сервиса (`directory/005-terminal-status.xml` и
    `pbl/005-terminal-status.xml`), каждый под своим преконтролем: таблицу создаёт тот, кто
    стартовал первым, и колонка нужна обоим (P1-2).

## 3. API Контракты (Эндпоинты `directory`)

Все эндпоинты защищены проверкой JWT токена (сигнатура валидируется ключом `HS256`).

### 3.1. Управление Компаниями (Companies CRUD)
-   `POST /api/v1/companies` — Создать компанию.  
    *Доступ*: Только `SYSTEM_ADMIN`.  
    *Запрос*: `{"id": "comp-01", "name": "MilliKart LLC"}`
-   `GET /api/v1/companies` — Получить список компаний. **Постранично с 22.08.2026 (P2-1)**.  
    *Доступ*: `SYSTEM_ADMIN` и `AUDITOR`.  
    *Параметры*: `page` (по умолчанию `0`), `size` (по умолчанию `20`) — те же умолчания и тот же
    потолок `200`, что у `GET /api/v1/audit-logs`. Значения срезаются, а не отклоняются:
    `?page=-1&size=0` отвечает `200`, а не `500`. С 24.08.2026 (P3-1) — `search`: подстрока без
    учёта регистра по `name` и `id`; `%` и `_` ищутся буквально; пустая строка — то же, что
    отсутствие параметра, длиннее 100 символов — обрезается. `totalElements` считает
    отфильтрованное.  
    *Порядок*: по `name`, при совпадении — по `id`. Довесок обязателен: без него две компании
    с одинаковым названием могут попасть на обе соседние страницы или ни на одну.  
    *Ответ*: `PagedResponse` — `{"content": [...], "totalElements", "totalPages", "size", "number"}`
    (раньше был голый массив). Компании со статусом `DELETED` не входят ни в `content`, ни
    в `totalElements` — фильтр выполняется в запросе.
-   `GET /api/v1/companies/{id}` — Детали компании.  
    *Доступ*: `SYSTEM_ADMIN`, а также `COMPANY_HEAD`/`COMPANY_MANAGER` (только своей компании).
-   `PATCH /api/v1/companies/{id}` — Редактировать компанию.  
    *Доступ*: Только `SYSTEM_ADMIN`.
-   `DELETE /api/v1/companies/{id}` — Удалить/деактивировать компанию.  
    *Доступ*: Только `SYSTEM_ADMIN`.

### 3.2. Управление Терминалами (Terminals CRUD)

Запись (create / update / delete) разрешена только ролям из `TerminalService.TERMINAL_WRITE_ROLES`
= `SYSTEM_ADMIN`, `COMPANY_HEAD`, `COMPANY_MANAGER`. Роль проверяется **до** `companyId`, поэтому
`COMPANY_EMPLOYEE`, `AUDITOR` и любая нераспознанная роль получают `403` даже на терминалы своей
компании (P1-15, 17.08.2026). Чтение шире: свои терминалы видят все компанейские роли, включая
`COMPANY_EMPLOYEE`, а `SYSTEM_ADMIN` и `AUDITOR` — все.

-   `POST /api/v1/terminals` — Создать терминал.  
    *Доступ*: `SYSTEM_ADMIN` (для любой компании), `COMPANY_HEAD`/`COMPANY_MANAGER` (только для своей компании).  
    *Запрос*: `{"id": 998877, "name": "Main Terminal", "login": "term_login", "password": "term_password", "companyId": "comp-01"}`
-   `GET /api/v1/terminals` — Список терминалов. **Постранично с 22.08.2026 (P2-1)**.  
    *Доступ*: `SYSTEM_ADMIN` и `AUDITOR` (все), `COMPANY_HEAD`/`COMPANY_MANAGER`/`COMPANY_EMPLOYEE`
    (только терминалы своей компании; без `companyId` — `403`).  
    *Параметры*: `page` (`0`), `size` (`20`, потолок `200`) — значения срезаются, а не отклоняются.
    С 24.08.2026 (P3-1) — `search`: подстрока без учёта регистра по `name`, `login`, `id` (как
    тексту), `companyId` и **названию компании**; `%` и `_` ищутся буквально; пустая строка — то
    же, что отсутствие параметра. Поиск работает **внутри** ролевого скоупа: компания видит только
    свои терминалы, что бы ни искала.  
    *Порядок*: по `name`, при совпадении — по `id`.  
    *Ответ*: `PagedResponse` (раньше — голый массив).
-   `GET /api/v1/terminals/options` — **лёгкий список терминалов** для выпадающих списков и
    подстановки имён (решение Р-45, 22.08.2026).  
    *Доступ*: тот же, что у `GET /api/v1/terminals`.  
    *Ответ*: голый массив из трёх полей, без пагинации:
    ```json
    [ {"id": 998877, "name": "Main Terminal", "status": "ACTIVE"} ]
    ```
    **Учётных данных терминала (`login`, `password`) здесь нет вовсе** — не замаскированы,
    а отсутствуют в DTO: полем, которого нет, нельзя случайно поделиться.

    **Заблокированные терминалы в ответе есть, и убирать их нельзя.** У эндпоинта два
    потребителя с разными нуждами: форме создания ссылки нужны только `ACTIVE` (на
    заблокированном терминале бэкенд откажет — P2-8), а экрану транзакций и карточке транзакции
    нужны **все**, потому что они подставляют имя терминала в старые платежи, и по снятому
    с обслуживания терминалу имя должно остаться. Поэтому фильтрует потребитель, а не сервер.
-   `GET /api/v1/terminals/{id}` — Детали терминала.  
    *Доступ*: `SYSTEM_ADMIN`, `AUDITOR`, любая роль с `companyId` терминала (в т.ч. `COMPANY_EMPLOYEE`).
-   `PATCH /api/v1/terminals/{id}` — Редактировать учетные данные терминала **и его статус**.  
    *Доступ*: `SYSTEM_ADMIN`, `COMPANY_HEAD`/`COMPANY_MANAGER` (своей компании).  
    *Запрос* (все поля необязательны): `{"name": "...", "login": "...", "password": "...", "companyId": "...", "status": "ACTIVE" | "BLOCKED"}`
-   **`DELETE /api/v1/terminals/{id}` больше нет** — метод отвечает `405` (путь существует, глагол не поддерживается).

> **Терминалы не удаляются, а блокируются** (P2-8, 21.08.2026, решение Р-37). Терминал, через
> который прошёл хоть один платёж, удалить нельзя в принципе: на него ссылаются платёжные ссылки
> (`fk_payment_links_terminal`), и попытка удаления возвращала `500` вместо внятного отказа.
> Вместо удаления — `status`:
>
> - `ACTIVE` — терминал в работе (значение по умолчанию для всех существующих терминалов);
> - `BLOCKED` — терминал выведен из работы.
>
> **Блокировка запрещает только новые платежи** (Р-38): создание ссылки на таком терминале — `400`,
> открытие ссылки плательщиком — отказ. Возвраты, списание холдов DMS и проверка статуса по уже
> прошедшим платежам продолжают работать; убирать эти исключения нельзя — иначе холд зависнет на
> карте клиента, а возврат не дойдёт до плательщика.
>
> **Блокировка приостанавливает ссылки терминала** (Р-39): `ACTIVE` → `SUSPENDED` одним `UPDATE`
> в той же транзакции, что и смена статуса терминала. `EXPIRED`, `COMPLETED` и `CANCELED` не
> трогаются. Разблокировка (Р-40) возвращает `SUSPENDED` → `ACTIVE`, а тем, у кого срок истёк за
> время блокировки, ставит `EXPIRED`. Обе операции пишутся в журнал аудита отдельными действиями
> `BLOCK` / `UNBLOCK` с числом затронутых ссылок в `details`.
>
> Блокировка **локальна для портала**: в MilliKart терминал продолжает работать, и платёж,
> начатый в обход портала, пройдёт (`problems.md`).

### 3.3. Журнал аудита (Audit Logs)

-   `GET /api/v1/audit-logs` — Журнал действий над компаниями и терминалами.
    *Доступ*: `SYSTEM_ADMIN` и `AUDITOR` — записи всех компаний; `COMPANY_HEAD`/`COMPANY_MANAGER` —
    только своей компании; остальные роли — `403` (и сам отказ записывается в журнал).
    *Параметры* (все необязательные и **независимые** — с 24.08.2026, P3-1; до этого
    `entityType` без `entityId` молча игнорировался): `entityType` (сравнение без учёта
    регистра), `entityId` (без учёта регистра), `search` — подстрока без учёта регистра по
    `performedBy`, `action`, `entityId` и `details`, `%` и `_` ищутся буквально; `outcome`
    (`SUCCESS` / `DENIED` / `UNRESOLVED`, неизвестное значение — как отсутствие фильтра);
    `from` и `to` — граница по `createdAt`, ISO-instant (`2026-08-24T10:15:30Z`) или просто дата
    (`2026-08-24` — весь день по UTC), неразбираемое значение — как отсутствие фильтра;
    `page` (по умолчанию `0`), `size` (по умолчанию `20`) — те же умолчания, что у
    `GET /api/v1/transactions` в `pbl`. Значения срезаются, а не отклоняются: `size` приводится
    к диапазону `1…200`, `page` — не меньше нуля, поэтому `?size=0` отвечает 200, а не 500.
    *Ответ* (с 21.08.2026 пагинированный — `PagedResponse`, раньше был голый массив):
    ```json
    {
      "content": [
        {
          "id": "…", "entityType": "COMPANY", "entityId": "comp-01", "action": "CREATE",
          "performedBy": "admin@millikart.az", "companyId": "comp-01",
          "details": "Created company: MilliKart LLC",
          "clientIp": "203.0.113.9", "outcome": "SUCCESS", "createdAt": "…"
        }
      ],
      "totalElements": 1, "totalPages": 1, "size": 20, "number": 0
    }
    ```
    Порядок — всегда от новых к старым (`createdAt DESC`, при равенстве — `id DESC`: одна
    операция пишет несколько событий в одну миллисекунду, и без уникального довеска записи с
    равным временем прыгали бы между страницами — P3-1). `outcome` — `SUCCESS`, `DENIED` или
    `UNRESOLVED` (с 24.08.2026, P3-2): успешное действие записывается **после коммита** его
    транзакции (откатившееся действие в журнал не попадает), отказ в доступе — сразу, в своей
    транзакции (Р-35); `UNRESOLVED` — денежная операция, исход которой эквайер не подтвердил:
    локальная транзакция откатилась, и эта запись — единственный след, по которому сверяются
    с эквайером. `clientIp` — адрес клиента по правилам `ClientIp` (заголовкам верим только от
    доверенного прокси); `null`, если действие выполнено вне HTTP-запроса. У записи об отказе
    `companyId` — компания **того, кто пытался**, а не та, что названа в запросе (иначе через
    отказ можно было бы писать текст в обзор аудита чужой компании); что именно пытались
    сделать, видно в `entityId` и `details`. Журнал только пополняется — записи не правятся и не
    удаляются (приложение физически не умеет: у репозитория записи один метод `save`, у сущности
    нет сеттеров). С 22.08.2026 (P2-14) сюда попадают записи **всех трёх сервисов**: `directory`
    — компании и терминалы, `auth` — учётные записи и аутентификация (`entityType` `USER` и
    `AUTH`), `pbl` — ссылки и деньги (`PAYMENT_LINK`, `TRANSACTION`). С 24.08.2026 (P3-2)
    значения `entityType` и `action` заданы общим словарём (`AuditEntity` / `AuditAction` в
    `common`); полная таблица событий — что лежит в `entityId`, кто пишет, что в `details` — в
    `technical_handover.md` §4.4. Машинерия записи общая, в `az.millikart.common.audit`; читает
    журнал только этот эндпоинт.

> **Кэширования в `directory` нет.** `getTerminal` и `getCompany` были помечены `@Cacheable(key = "#id")`
> с проверкой прав внутри тела метода: при попадании в кэш тело не выполнялось, вместе с ним
> не выполнялась и проверка, и сотрудник чужой компании получал данные терминала. 17.08.2026
> аннотации сняты целиком (P0-3, решение Р-9). `CacheConfig` в `common` оставлен под будущий кэш
> в `pbl` — не возвращай `@Cacheable` на методы, внутри которых есть проверка доступа.
